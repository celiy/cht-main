Instalação a partir do workspace do usuário:
    Pastas tipo .vscode, .cursor, .prettierignore, .prettierrc.json, netlify.toml agora devem ficar dentro de uma pasta dedicada, comando de install recebe nova flag: --new onde o usuário poderá configurar como ele quer que o projeto siga.

    Ao executar com esse new, ele irá perguntar a IDE que ele está usando, no momento terá apenas o vscode como opção, então ao selecionar vscode, ele irá criar uma .vscode vazia e básica. Depois a mesma lógica para o prettier, perguntar se ele quer instalar o prettier, criar configuração vazia do prettier. Depois arquivo de configuração de vps, por enquanto temos apenas o netlify.toml, então apenas copiar o netlify atual padrão. 

    Depois de tudo isso, ele irá perguntar se ele quer salvar esta configuração de workspace atual, se sim, ele vai selecionar o cliente que ele quer salvar esta configuração. Então por exemplo, no meu caso de uso, esta configuração atual de arquivos que listei ficaria dentro do devApp. Então se um cliente que utiliza o cht já ter esta pasta com os arquvios de workspace pré montados, ao rodar o install, uma flag para copiar esses arquivos para o root do cht-main: --workspace:[nome].

Documentação de contribuição:
    Fazer um documento padrão de contribuição, guiar IAs a ler eles caso precisem para fazer alguma contribuição ao repositório.

    A documentação deve ter o padrão de código, como ele deve ser escrito, o que é esperado do código e a sua qualidade. 

    Se o usuário quiser contribuir a um componente, ele tem que ter em conta que o componente não deve ter sua funcionalidade base mudada e sim adicionada ou melhorada. O componente não pode ser mudado num valor profundo que o faça perder sua funcionalidade ou quebrar em casos de uso que ele já exista (como os casos de uso na documentação). Isso significa que um componente tipo o Select já está pronto para uso e implementado, mas se alguma alteração for feita que exige que códigos que usam este componente precisam ser mudados, então este tipo de alteração não será aceita. 

    Agora, componentes que não foram implementados completamente ou estão em processo de evolução, são componentes que podem sim serem mudados e terem certas excessões, componentes que tem o estado de "Em implementação" ou "Em evolução" são os que caem nesta regra de excessões. O status de cada componente está nos docs.
